# addrmatch — локальный матчер адреса со справочником

Резервный путь для HR-бота: когда внешний геокодер отказал (квота, недоступность, точность
«до города»), матчер сопоставляет кривую строку (после ASR или из чата) с эталонным
справочником локально, без сети. Возвращает не «ответ/отказ», а решение для диалога:
ответить, ответить с мягким подтверждением, подтвердить, спросить город/дом/улицу или
честно отказаться — это прямой ответ на боль ТЗ «бот переспрашивает адрес по кругу».

Полная концепция (контракты блоков, гипотезы, план) — `docs/concept.md`. Ниже —
пошаговое описание готового решения и цифры по критериям приёмки.

## 1. Запуск

```bash
pip install -r requirements.txt
```

Точка входа ТЗ:

```bash
python run.py --adresses test_task_adress_match/data/adresses_labeled.jsonl \
              --etalon test_task_adress_match/data/etalon.jsonl \
              --predictions preds.jsonl
```

Печатает в stdout ровно один JSON с 9 ключами ТЗ (`n`, `n_positive`, `n_negative`, `top1`,
`top3`, `reject_precision`, `reject_recall`, `ms_per_request_p50`, `ms_per_request_p95`).
`--predictions` пишет `{id, candidates, scores}` построчно.

Флаги:

| Флаг | Значения | Смысл |
|---|---|---|
| `--predictions PATH` | путь | выгрузить predictions отдельно от метрик |
| `--ranker` | `manual`\|`logreg` | какой ранкер использовать; без флага — `manual` (см. §4, §7) |
| `--ablate` | `whole_string`\|`no_phonetic` | абляции для §3 (матч целой строкой / без фонетики) |
| `--N` | число (default 10) | стоимость ложного `answer` в переспросах (N4) |
| `--channel` | `voice`\|`webchat` | посчитать метрики только по одному каналу |

Тесты (112 штук):

```bash
PYTHONUTF8=1 python -m pytest -q
```

Вспомогательные инструменты (`tools/`), каждый — самостоятельный CLI-отчёт:

```bash
python tools/check_preds.py preds.jsonl --expect 500          # формат predictions
python tools/check_parser.py --adresses ... --etalon ...      # метрики Parser (house/cues)
python tools/errors_report.py --adresses ... --etalon ...     # разбор ошибок -> docs/errors-a4.md
python tools/train_ranker.py --adresses ... --etalon ... --seed 42   # обучение логрег-ранкера
python tools/simulate_dialog.py --adresses ... --etalon ...   # симуляция дозапроса (H12)
```

На Windows нужен `PYTHONUTF8=1` перед `python`, иначе консоль ломает кириллицу в логах.

## 2. Подход: что делаем со строкой и почему

Конвейер (`docs/concept.md` §5):

```
raw, channel, slots ──► Normalizer ──► Parser ──► Index.candidates() ──► имена
                                                       │
                                          Index.resolve_city() ──► город (приор)
                                                       │
                                          Index.resolve_objects() ──► кандидаты-объекты
                                                       │
                                          Ranker.score() ──► p (калиброванная)
                                                       │
                                          Index.houses() для top-M ──► эталоны
                                                       │
                                          Decider(N) ──► decision, candidates, options, explain
```

### Normalizer — строка → строка (`addrmatch/normalizer.py`, `numerals.py`)

Регистр, `ё→е`, латиница-двойники (webchat печатают адрес английской раскладкой), стоп-слова
(«это», «короче», «вот»), сокращения (`ул.` → `улица`, `пр-т` → `проспект`, `д.`/`к.`/`корп.`/
`стр.`/`лит.`), числительные словами → цифры (`numerals.py`: 1–999 с фонетическими вариантами
типа «дватцать васемь» → 28), склейка хвоста дома («18 а» → «18а», «к а» → «кА»). Модуль ничего
не знает про справочник (N5, проверено тестом графа импортов) — переиспользуется в любом
пайплайне, где нужно вычистить ASR-мусор из строки.

**Почему отдельным шагом, а не внутри Parser**: числительные и мусор — общая для голоса и чата
проблема, а разрез улица/дом — специфика адреса. Разделение держит `numerals.py` пригодным для
телефонов, ФИО, любых числовых полей.

### Parser — строка → слоты (`addrmatch/parser.py`)

Регулярки: тип улицы из словаря типов (типы приходят из справочника через Index — не зашиты в
Parser), дом = первое число с хвостом корпус/строение/литера (`16`, `16а`, `16к2`, `16/2`,
`16-18` → диапазон + флаг, `д.16 кв.5` → квартира отбрасывается), улица = токены между типом и
домом. `has_address_cues` = есть тип ИЛИ дом ИЛИ токен из словаря имён Index — отличает «не
про адрес» от кривого адреса ещё до похода в индекс.

**Почему дом разбирается отдельно от улицы, а не единым фаззи-матчем по всей строке**: в
эталоне на одну улицу — до 10 домов, и один и тот же символьный шум («3» вместо «3к1») бьёт
по дому и по улице по-разному. Абляция `--ablate whole_string` (матч всей строки без разреза)
показывает эффект напрямую — см. §3.

**Город Parser не извлекает**: неопознанные токены до типа улицы уходят в `city_hint`,
разрешение города — задача Index (см. ниже).

### Index — справочник → поиск (`addrmatch/index.py`)

Три единицы: **имя** улицы (словарь, в учебной базе 699 уникальных имён), **объект**
(имя × город × тип) и **эталон** (улица × дом). Поиск имени — три дешёвых сигнала:
русский фонетический ключ (оглушение звонких, редукция гласных, усечение окончаний —
ловит «пирвомайсгий» ↔ «первомайский»), Дамерау-Левенштейн + token_set (символьные опечатки
webchat), char-3-грам cosine (слипания «горькогосто» → «горького сто»). Город — фаззи-резолв
по 8 городам (`resolve_city`), но **не фильтр**: `candidates()` ищет имя по всему словарю, город
подмешивается на следующем шаге как приор в `resolve_objects()`.

**Почему город не фильтр (K5, `docs/triz-resolution.md` Т1)**: в 37/500 строк labeled город
пустой, ещё часть — с опечаткой или вовсе чужим городом. Жёсткий фильтр по городу на этих
строках убивает правильную улицу из кандидатов без права на восстановление. Блокинг по
словарю имён (а не по городу) даёт ту же скорость — на ГАР (163 152 уникальных имени против
1 221 748 улиц-объектов, см. §7) словарь имён на порядок меньше объектов и сам по себе
достаточно мал для полного перебора. При кривом городе улица всё равно находится по имени,
и решение уходит в `ask_city`, а не в промах.

**Почему три сигнала, а не один и не эмбеддинги**: фонетика ловит искажения на слух,
Левенштейн — опечатки набора, n-граммы — слипания слов. Один сигнал не покрывает оба канала
(voice и webchat шумят по-разному, см. §4 про эмбеддинги).

### Ranker — фичи кандидата → p (`addrmatch/ranker.py`)

Таблица фичей (значение при отсутствии сигнала — в скобках): `lev`, `token_set`, `phon`,
`ngram` (0), `alias_hit` (0), `type_match` (0.5), `city_match` (0.5), `house_found`,
`house_in_list` (0), `channel_voice`, `name_freq`, `n_close` (число кандидатов в пределах
0.05 от лидера), плюс interaction-фичи `freq×city`, `freq×phon`, `voice×lev`, `sim×house`.
`ManualRanker` — ручные веса через сигмоиду (docker по умолчанию), `LogregRanker` —
sklearn-логрег с пост-калибровкой по стратам (см. §4, §7 — почему не по умолчанию).
`explain()` раскладывает скор лидера по сигналам — обязательное требование объяснимости (N6).

### Decider — ранжированный список → исход (`addrmatch/decider.py`)

Семь исходов: `answer`, `answer_soft` (записываю адрес как неявное подтверждение — «если
ошибся, поправьте»), `confirm`, `ask_city`, `ask_house`, `ask_street`, `reject`. Пороги не
подбираются руками — выводятся из одного бизнес-числа N («один ложный `answer` стоит N
переспросов», ТЗ: «уверенный ложный матч дороже переспроса»): `answer`, если
`p ≥ N/(N+1)` (при N=10 → p ≥ 0.909). Порядок правил фиксирован (§5.5 concept.md):
`reject`(нет cues) → `ask_city`(частое имя + город не разрешён) → `ask_house`(улица уверена,
дом не найден/не в списке) → `answer*`/`confirm`(по цене) → `ask_street` → `reject`. Проекция
в формат ТЗ: `answer*`/`confirm` → до 3 эталонов по p; `ask_house` → до 3 домов лидера-улицы;
`ask_city` → эталоны лидера в предложенных городах; `ask_street`/`reject` → `[]` (пустой список
= отказ по контракту ТЗ).

**Почему семь исходов, а не бинарный ответ/отказ**: боль заказчика — «бот переспрашивает
адрес по кругу» целиком. Точечный дозапрос («какой дом?» вместо «повторите адрес») сужает
следующий ввод до одного слова — ASR ошибается реже, а повторный `match()` принимает слот-id
как точный фильтр. Симуляция в §3 показывает, что это реально работает.

### Четыре примера «вход → что получили»

| raw (channel) | normalize | parse | decision |
|---|---|---|---|
| `микрорайон пирвомайсгий 23` (voice) | `микрорайон пирвомайсгий 23` | type=микрорайон, street=пирвомайсгий, house=23 | `answer` → e_0107, p=0.998 (фонетика поймала «пирвомайсгий» ↔ «первомайский») |
| `мой адрес: ул. Прокопия Галуина 14` (webchat) | `улица прокопия галуина 14` | type=улица, street=прокопия галуина, house=14 | `answer` → e_0795 (сокращение раскрыто, дом цифрами — webchat без ASR-шума) |
| `мне удобно на проспект ленинградский три один` (voice) | `проспект ленинградский 3 1` | type=проспект, street=ленинградский, house=3 | `ask_house` → улица уверена (p=0.993 на всех троих), но «три один» распарсилось как дом `3`, а не `3к1` — Decider честно переспрашивает дом вместо угадывания |
| `да куда скажете туда и приду` (voice) | без изменений | cues=False, street/house не найдены | `reject` — ни типа улицы, ни дома, ни имени из словаря; негатив вида 1 пойман до похода в индекс |

## 3. Результаты

Прогон `run.py` на `adresses_labeled.jsonl` (500 строк, ручные веса — дефолт):

| Метрика | Значение | Порог ТЗ/H |
|---|---|---|
| top1 | **0.9725** | H1 ≥ 0.85 |
| top3 | **0.98** | — |
| reject_precision | **0.9659** | — |
| reject_recall | **0.85** | — |
| ms_per_request p50 | **1.28 мс** | — |
| ms_per_request p95 | **1.55 мс** | H6 ≤ 10 мс, ТЗ ≤ 200 мс |

112/112 тестов pytest зелёные.

### Абляции (H1a, H2)

| Абляция | top1 | Δ к базе | Вывод |
|---|---|---|---|
| база (разрез + 3 сигнала) | 0.9725 | — | — |
| `--ablate whole_string` (матч всей строки, без разреза улица/дом) | **0.60** | −37.3 п.п. | разрез критичен — дом делает работу, которую фаззи-матч по всей строке не делает |
| `--ablate no_phonetic` (без фонетического ключа) | **0.97** | −0.3 п.п. | на этом датасете фонетика почти не нужна — Левенштейн + n-граммы уже ловят большинство ASR-замен; ключ оставлен как задел под словарь на порядок больше (ГАР, §7), где редких искажённых имён будет заметно больше |

H1a подтверждена (разрез даёт огромный прирост), H2 — нет: гипотеза «фонетика даёт ≥5 п.п.»
не подтвердилась на этих 500 строках. Честно фиксируем расхождение, а не подгоняем формулировку.

### Разбор ошибок (docs/errors-a4.md, tools/errors_report.py)

Позитивы: 389/400 top1_hit (0.9725). Промахи (11):

| Класс | Число | Причина |
|---|---|---|
| house_mismatch | 4 | все 4 — точные дубликаты адресов в эталоне (одинаковые city/street_type/street/house под двумя `etalon_id`), любой из двух правильный, промах неустраним без правки эталона |
| wrong_ranking | 3 | верная улица, но дом не в списке кандидатов из-за среза числительного («три один» → `3`, ожидалось `3к1`) — Decider уходит в `ask_house`, не угадывает |
| rejected_positive | 3 | 2 — слипание слов без пробела («улица95 гвардейской»), Parser не смог отделить дом; 1 — искажение имени сильнее, чем ловят три сигнала |
| wrong_object | 1 | коллизия домов на похожих по фонетике улицах в разных городах при неверном городе в разметке |

Негативы (100): 84 отклонены верно, **16 приняты** (все — тип 2, «реальная улица не из
эталона с домом, случайно совпавшим на похожей по имени улице»); ложных принятий негативов
типа 1 («не про адрес») — 0.

| answer_soft | 2 | 3 |
| confirm | 0 | 7 |

### Parser: точность разбора (tools/check_parser.py)

- дом выделен в **96.25 %** строк, где он есть в эталоне (385/400), цель ≥ 95 % — выполнена;
- тип улицы найден в **100 %** строк с типом;

### Симуляция диалога (H12, tools/simulate_dialog.py)

Естественные исходы (мало данных, но индикативно):

| Сценарий | n | доля разрешённых после дозапроса |
|---|---|---|
| `ask_house` → второй `match()` с истинным домом | 11 | 0.909 |
| `ask_city` → второй `match()` с истинным городом | 4 | 1.0 |

Форсированные (статистическая сила — дом/город убираются у каждого позитива искусственно):

| Сценарий | n | доля |
|---|---|---|
| дом срезан из raw → доля строк, где первый ход дал `ask_house` | 399 | 0.832 |
| после подачи истинного дома → `answer`/`answer_soft` | 332 | **0.958** |
| город обнулён → второй ход с истинным city_id → `answer`/`confirm` | 70 | **0.957** |

Дозапрос реально работает: сужение до одного слота почти всегда разрешает диалог, даже когда
первый проход без этого слота ушёл бы в `reject`/`confirm` на неполных данных.

### Логрег-ранкер: почему не он по умолчанию

`tools/train_ranker.py --seed 42` (сплит 75/25, стратифицированный по каналу и негативам,
interaction-фичи, пост-калибровка Platt/изотоникой по стратам {channel}×{freq_class}×
{city_status}) на val-сплите:

| Гейт | Результат | Порог |
|---|---|---|
| H3 (ошибки `answer` при N=10) | 0 ошибок, покрытие `answer`+`answer_soft` 0.97 | ≤ 3 ошибок, покрытие ≥ 0.75 |
| H3a (калибровка) | макс. отклонение бина 0.012, train/val gap 3.6 п.п. | бин ≤ 0.1, gap ≤ 5 п.п. |
| H5 (негативы тип 2 → reject/ask_street) | 0.93 на val | ≥ 0.85 |

Калибровка честная. Но на **всех 500** строках `run.py --ranker logreg` даёт top1 **0.9525**
(vs 0.9725 ручных весов), top3 0.955 (vs 0.98), reject_precision 0.875 (vs 0.9659),
reject_recall 0.98 (vs 0.85 — логрег отказывает чаще и точность top1 проседает). Решающий
критерий — полный прогон, а не val-гейты: логрег системно завышает p «похожим-но-неверным»
объектам тип-2 (реальная улица не из эталона, но с домом, совпавшим на похожей по имени
улице) сильнее, чем ручные веса. По тайм-боксу A5 (1 час) по умолчанию остаются ручные веса:
`run.py` без флага всегда использует `manual` — детерминированно, независимо от файла модели
(`addrmatch/ranker_model.json` поставляется с `meets_gates: false` как отметка результата
обучения, на выбор ранкера она не влияет). `--ranker logreg` включает логрег явно, для
экспериментов. Идеи по улучшению — §7.

## 4. Что пробовали и отбросили

Полный разбор вариантов с плюсами/минусами — `docs/approaches.md`. Коротко, что не пошло в базу:

| Подход | Почему отбросили |
|---|---|
| Sentence-эмбеддинги (rubert-tiny2/e5-small/bge-m3) + cosine | обучены на смысл, слепы к фонетике: «киравсгой» и «Кировская» — разные токены, на опечатках уступают char-n-граммам; тянут torch, латентность 20–80 мс CPU против <1 мс у трёх сигналов |
| LLM в запросе (реранкер / нормализатор zero-shot) | 300 мс+ на GPU, требует GPU в резервном пути — ломает и N2 (CPU-only), и p95; локализация возможна только офлайн (см. §7) |
| Жёсткий фильтр по городу (город как ключ блокинга) | при пустом/кривом городе (37+ строк из 500) отрезает верную улицу без права на восстановление — заменено на блокинг по словарю имён + город как приор (K5, `docs/triz-resolution.md` Т1) |
| Логрег вместо ручных весов | обучен, калибровка честная, но хуже ручных весов на полном прогоне (§3) — оставлен как опция за флагом |
| Матч целой строкой (без разреза улица/дом) | top1 0.60 против 0.9725 — прямое измерение абляцией (H1a) |
| Готовые парсеры адресов (libpostal, Natasha) | libpostal — 2 ГБ данных и тяжёлая установка, не заточен под ASR-шум; Natasha — правила, не разбирает «сорок восемь короче бэ» |
| Cross-encoder реранкер поверх top-20 | 20 проходов × 10 мс на CPU = сотни мс, не укладывается в 200 мс ТЗ даже с запасом |

## 5. Где ломается

| Класс | Пример | Причина |
|---|---|---|
| Дубликаты эталона | `e_0500`/`e_0612`-подобные пары с одинаковыми city/street_type/street/house | 4 промаха top-1 из 11 — оба ответа верны, но метрика засчитывает только один `etalon_id`; неустранимо без правки справочника |
| Числительное-паттерн «N N» вместо «N корпус M» | «три один» → дом `3`, ожидалось `3к1` | по спеке уходит в `ask_house` (честный дозапрос), а не угадывание — 3 случая |
| Слипание слов без пробела на границе улица/дом | «улица95 гвардейской 10» | Parser не всегда режет число, слипшееся с предыдущим словом |
| Негативы тип 2 (похожая улица не из эталона) | «республ иканская 6» → похожая по фонетике улица другого города с совпавшим домом | 16/100 негативов приняты — главный нерешённый класс ошибок, все ложные принятия негативов на этом датасете именно такие |
| Слот-город кривой/пустой без ГАР | 37/500 строк с пустым городом в labeled | на учебной базе (8 городов) не критично — на ГАР (десятки тысяч населённых пунктов) потребует `resolve_city` по гораздо большему словарю (H8a, ещё не реализовано) |

Ограничения данных: 500 размеченных строк — мало для устойчивого обучения логрега (риск
подгонки под шум конкретного датасета, см. §3); негативы тип 2 никак не размечены отдельно
от тип 1 — их пришлось классифицировать эвристикой (`tools/errors_report.py`), а не по метке.

## 6. Как замеряли время

Железо: Intel Core i9-10920X 3.5 GHz, 128 ГБ RAM, Windows 11, Python 3.12.3; версии библиотек
закреплены в `requirements.txt` точно (`==`): rapidfuzz 3.14.6, scikit-learn 1.9.1, numpy 2.5.3.

В замер входит только `Matcher.match()` (normalize → parse → поиск имён → resolve_objects →
фичи → Ranker.score → Decider.decide → проекция), монотонные часы `time.perf_counter()` вокруг
каждого вызова. **Загрузка эталона и построение индекса (словарь имён, предпосчитанные
фонетические ключи и n-грам матрица, ~1 с на 1000 эталонов) — вне замера**, как и предлагает
ТЗ («загрузка эталона и прогрев обычно делаются один раз»). Замер однопоточный, без отдельного
прогрева — первый вызов `match()` уже входит в p50/p95 (BruteForceIndex ничего не кеширует
лениво, все структуры готовы после `__init__`).

Итог: p50 ≈ 1.3 мс, p95 ≈ 1.5–1.6 мс — на два порядка быстрее мягкого порога ТЗ (200 мс) и
жёстче собственной цели H6 (≤ 10 мс на учебной базе).

**Про закрепление версий.** Первый вариант `requirements.txt` задавал только нижние границы; на
чистом venv подтягивался numpy 2.x вместо 1.26 из dev-окружения, и `reject_precision`/`reject_recall`
сдвигались на одну строку из 100 (0.9663→0.9659, 0.86→0.85): фаззи-скоринг чувствителен к
минорным различиям rapidfuzz/BLAS. Поэтому версии закреплены точно, все цифры в этом readme —
из закреплённого окружения.

## 7. Что дальше

- **ГАР вместо учебной базы.** H7 подтверждён на реальном ГАР (`docs/gar-h7-result.json`):
  1 221 748 актуальных улиц, но всего **163 152** уникальных нормализованных имени — 218 самых
  частых покрывают половину улиц; 160 474 населённых пункта (5+6 уровень ГАР), 83 547
  уникальных имени; 76 типов улиц против 10 в учебном эталоне. Архитектура уже под это:
  словарь имён (слой 1, тот же движок из трёх сигналов) → отображение имя→объекты (слой 2,
  город как приор) → дома внутри выбранной улицы (слой 3). Реализация — `NameVocab` с
  инвертированным индексом по триграммам/фонетическим ключам вместо `cdist` по всем именам
  (H8: цель ≤ 20 мс с городом / ≤ 50 мс без), `resolve_city` по населённым пунктам тем же
  движком (H8a).
- **LLM офлайн для генерации ASR-вариантов имён.** Не в запросе (латентность/GPU — см. §4),
  а при сборке индекса: по словарю имён генерируются искажённые варианты («киравсгой» и
  подобные), из них — расширенный словарь алиасов (`alias_hit`), матрица замен для
  взвешенного Левенштейна, обучающая выборка для ранкера. GPU нужен один раз офлайн, в
  `match()` его нет (`docs/triz-resolution.md` Р2.1).
- **Логрег: что нужно, чтобы обогнать ручные веса.** По разбору ошибок (§3) логрег путает
  похожие-но-неверные объекты тип-2. Кандидаты фичей: `margin` (отрыв p₁−p₂ явной фичой, не
  только через `n_close`), `max_house_match_any` (совпадение дома с любой, не только
  лидирующей, улицей — требует второго прохода по Index, сейчас `resolve_objects` вызывается
  один раз на топ имён); отдельная разметка негативов тип-1/тип-2 (сейчас классифицируются
  эвристикой, не меткой); синтетика по словарю имён (см. пункт про LLM) для расширения 500
  строк.
- **`answer_soft` в диалоге бота.** Матчер уже отдаёт этот исход (проецируется в `answer`
  формата ТЗ), но снижение цены ошибки за счёт неявного подтверждения («записываю Кировская
  16, если ошибся — поправьте») работает только если бот произносит эту фразу, а не молча
  подставляет адрес — это решение на стороне бота, не матчера.
- **Дозапрос по слотам через API.** Контракт уже готов:
  `match(raw, channel, slots, asked_slot, scope) -> MatchResult`. `slots` принимает текст
  (фаззи, приоритет над `raw`) либо `{"id": ...}` (точный фильтр из `options` предыдущего
  ответа); `asked_slot` снимает требование `has_address_cues` на ответ на прямой вопрос;
  `scope` сужает поиск списком `city_id`. Матчер stateless — состояние диалога живёт у бота,
  что и позволяет переиспользовать его в звонке, чате и форме без изменений.
- **`requirements.txt` с закреплёнными версиями** — см. наблюдение в §6.
