# addrmatch — концепция продукта и план разработки

Версия 0.2, 2026-09-12. Автор: Иван (с Claude). Статус: после внутреннего аудита спецификации и ТРИЗ-разрешения противоречий (`triz-resolution.md`). Изменения к v0.1 отмечены «(v0.2)».

## 1. Что это

Локальная библиотека сопоставления кривой строки адреса (после ASR или из чата) с эталонным справочником. Возвращает не «ответ/отказ», а решение для диалога: ответить, ответить с мягким подтверждением, подтвердить, спросить город/дом/улицу, отказаться.

Первый потребитель — HR-бот (тестовое задание: 1000 эталонов, 8 городов). Целевой — любой пайплайн Ивана, где из речи/текста надо вытащить адрес и привязать его к справочнику вплоть до полного ГАР по всей России.

## 2. Контекст и боль

- Основной путь — внешний геокодер (< 40 мс). Отказы: квота, недоступность, точность «до города».
- При отказе бот «переспрашивает адрес по кругу»: человек повторяет всю фразу, ASR снова ошибается.
- ТЗ: «уверенно сопоставленный негатив дороже лишнего переспроса, но и отказываться на всём подряд смысла нет» — штрафуются оба хвоста, ложный матч дороже.
- Персональные данные не покидают контур: инференс матчера локальный (ASR бота — вне нашего периметра).

## 3. Требования

### Функциональные
- F1. Вход: `raw` строка; канал `voice|webchat`; необязательные слоты `city`, `street_type`, `street`, `house` — каждый либо текст из реплики (фаззи), либо канонический id из `options` предыдущего ответа (точный фильтр) (v0.2); `asked_slot` — какой слот бот спрашивал (v0.2); `scope` — область поиска: список city_id / регион / None (v0.2).
- F2. Выход: `decision ∈ {answer, answer_soft, confirm, ask_city, ask_house, ask_street, reject}` (v0.2: + `answer_soft`), ранжированные `candidates` (эталоны улица+дом, ≤ 3) + `scores` (калиброванные p), `missing_slot`, `options` (≤ 3 канонических значения для вопроса-выбора), `slots_resolved` (city_id, street_id, house — что именно подтверждаем), `explain` (разложение скора лидера по сигналам; для нейросетевых компонентов — вход/выход), `error` (v0.2).
- F3. Справочник подключается как данные: учебный JSONL, ГАР (SQLite), любой другой с полями город/тип/улица/дом.
- F4. Дозапрос заполняет слот; повторный вызов сужает кандидатов: слот-id — точный фильтр, слот-текст — фаззи с приоритетом над raw. Матчер stateless, состояние диалога у бота.
- F5. Точка входа `run.py --adresses --etalon [--predictions]` печатает метрики JSON по формату ТЗ. `match()` не бросает исключений: ошибки → `reject` + `error`; ошибки загрузки — на `ready()` (v0.2).

### Нефункциональные
- N1. Латентность `match()` на прогретом индексе (ТЗ разрешает исключить загрузку и прогрев): учебная база p95 ≤ 10 мс; ГАР с разрешённым городом ≤ 20 мс, без города ≤ 50 мс; общий мягкий порог ТЗ 200 мс. Тяжёлые модели в `match()` не участвуют (v0.2, см. K7).
- N2. Никаких внешних вызовов на инференсе; CPU. `pip install -r requirements.txt && python run.py` на чистой машине. GPU допустим только на этапе сборки индекса/обучения (v0.2).
- N3. Масштаб: 1000 эталонов → ГАР без смены контрактов блоков; меняются реализации Index. Переносимы веса сигналов; **калибровка порогов — на каждую базу** (v0.2, П4).
- N4. Стоимость ошибки задаётся одним числом N: «один ложный `answer` = N переспросов». Пороги решений выводятся из N, не подбираются вручную (v0.2, Р3.2). Стартовое N = 10; уточняется с заказчиком.
- N5. Переиспользование: `numerals`, `normalizer`, фаззи-движок по словарям — модули без импортов из `index`/данных (проверяется тестом графа импортов).
- N6. Объяснимость базового пути: `explain` раскладывает скор лидера по сигналам. Для обученных компонентов — логирование входа/выхода (v0.2, П11).

## 4. Ключевые решения

Колонка «Основание»: *измерено* — есть данные; *оценка* — дизайн-рассуждение, проверяется гипотезой из §7.

| # | Решение | Почему | Основание | Отброшено |
|---|---------|--------|-----------|-----------|
| K1 | Разрез строки на улицу и дом, матч по отдельности | Дом решает top-1 (до 10 домов на улицу в учебной базе); улица и дом шумят по-разному | измерено (hist домов), H1 + абляция H1a | Матч целой строкой |
| K2 | Три дешёвых сигнала сходства улицы: фонетический ключ, Левенштейн (Дамерау-Левенштейн отброшен — `process.cdist` без SIMD-пути даёт ~2 мс на сигнал, см. index.py), TF-IDF по символьным 2–4-граммам (char_wb) cosine | Фонетика для voice, символьный для webchat, n-граммы для слипаний | оценка → H2 | Эмбеддинги (слепы к фонетике), LLM на запросе |
| K3 | Ранкер = логрег с interaction-фичами (`freq × city_match`, `freq × phonetic`, `channel × sim`) + пост-калибровка по стратам → p = честная вероятность в каждой страте (v0.2, Р3.1) | Один скор означает разную вероятность ошибки в разных стратах; лечим калибровку, не порог | оценка → H3, H3a | Ручные веса — baseline и fallback |
| K4 | Трёхслойный индекс: словарь имён улиц → имя→(город, тип, id) → дома | Уникальных имён на порядок меньше объектов; словарь почти закрыт; обученное учится на словаре | оценка → H7 | Перебор объектов |
| K5 | **Блокинг по словарю имён, не по городу** (v0.2, Р1.1). Город — слой 2 (имя → объекты в этом городе), фича ранкера и правило Decider по частотности имени (Р1.3). Запас: раскрывающийся радиус город → регион → страна при низком скоре (Р1.2) | Скорость даёт малый словарь имён; при кривом городе имя всё равно найдено → `ask_city`, а не промах | оценка → H8, H8a, H11 | Жёсткий фильтр по городу (промах шарда без восстановления) |
| K6 | Семь исходов вместо двух, точечный дозапрос; слоты-id из `options` для гарантированного сужения | Один слот проще расслышать; лечит «переспрос по кругу» | оценка → H12 | Бинарный ответ/отказ — остаётся проекцией в формат ТЗ |
| K7 | **Тяжёлая модель (LLM) — только офлайн** (v0.2, Р2.1): генерирует ASR-варианты имён по словарю → алиасы, матрица замен, обучающая выборка. В `match()` — CPU-мс. Направления: ночной «майнер ошибок» по логам (Р2.3), асинхронное обогащение во время ответа человека (Р2.2) | GPU нужен один раз при сборке; резервный путь остаётся лёгким | оценка → H9 | Каскад с LLM в запросе (ломает p95 и N2) |
| K8 | Синтетический шум по словарю имён: LLM-генерация вариантов (K7) + правила как fallback | Данных 500 строк; словарь имён компактен | оценка → H9 | TTS→ASR round-trip — в фазу C |
| K9 | Decider выбирает исход по минимальной ожидаемой цене при заданном N (v0.2, Р3.2); `answer_soft` («записываю Кировская 16, если ошибся — поправьте») снижает цену ошибки за счёт неявного подтверждения (Р3.3) | Точность и покрытие становятся следствием одной бизнес-ручки | оценка → H3a | Ручные τ_a/τ_c/δ |

## 5. Архитектура

```
raw, channel, slots, scope
   │
   ▼
Normalizer ─► Parser ─► Index.candidates(street_q, k, scope)   ─► имена
                              │  Index.resolve_city(city_q|id) ─► CityResolution
                              ▼
                        Index.resolve_objects(name_ids, CityResolution, scope) ─► кандидаты (имя×город×тип)
                              ▼
                        Ranker.score(features) ─► калиброванные p
                              ▼
                        Index.houses(street_id) для top-M ─► эталоны
                              ▼
                        Decider(costs N) ─► decision, candidates, options, slots_resolved, explain
```

### 5.1 Normalizer (строка → строка)
Вход: `str`, `channel`. Пустая строка проходит как пустая; > 512 символов обрезается с флагом `truncated`. Нижний регистр, ё→е, латиница-двойники → кириллица (webchat), удаление мусорных слов по стоп-списку, раскрытие сокращений (ул., пр-т, д., к., корп., стр., лит.), числительные словами → цифры («сто шестьдесят три» → 163, «два к два» → 2к2, «восемнадцать к а» → 18кА), склейка «18 а» → «18а». При неоднозначном числительном («сто, шестьдесят три») — первое прочтение + флаг `ambiguous_number`. Свойство: `normalize(normalize(x)) == normalize(x)` (тест). Не знает про справочник; стоп-список сверяется со словарём имён на стороне Index при загрузке (пересечение → предупреждение). Версия нормализатора хэшируется; индекс хранит хэш, при несовпадении — ошибка загрузки. Слоты-тексты нормализуются той же функцией; слоты-id не трогаются. Модуль `numerals.py` — отдельный, с тестами.

### 5.2 Parser (строка → слоты)
Регулярки: тип улицы из словаря типов (типы приходят из справочника через Index при загрузке); дом = первое число с хвостом корпус/строение/литера; улица = токены между типом и домом (или всё до дома). Формы дома: `16`, `16а`, `16к2`, `16/2` (= корпус), `16-18` (диапазон → `ask_house`), `д.16 кв.5` (квартира отбрасывается). Возвращает `{street_type?, street?, house?, corpus?, letter?, city_hint?, has_address_cues, ambiguous_number}`. `street` необязателен (ответ на дозапрос может быть одним словом). `has_address_cues` = тип улицы ИЛИ дом ИЛИ токен из словаря имён (`Index.has_name()`); при `asked_slot != None` флаг не требуется (Т4). Город Parser не извлекает — неопознанные токены до типа улицы уходят в `city_hint`. Слот побеждает raw для того же поля. Контракт стабилен: позже заменяется теггером без изменения выхода.

### 5.3 Index (справочник → поиск)
Единицы: **имя** (запись словаря имён), **объект** (имя × город × тип = улица), **эталон** (улица × дом). Интерфейс:
- `ready() -> bool`; вызов остальных методов до готовности — ошибка.
- `has_name(token) -> bool`.
- `resolve_city(city_q: str | CityId | None, scope) -> CityResolution{status: resolved|ambiguous(list)|unresolved|none, city_id?, score}`. Текст → фаззи по словарю населённых пунктов (в учебной базе — 8; на ГАР — ~150 тыс., тот же движок); id → точно; None/"" → `none`; лучший fuzzy < θ_city → `unresolved`.
- `candidates(street_q: str, k: int, scope) -> list[NameCand]` — top-k имён с сырыми фичами сходства (фонетика, Levenshtein, n-грам, alias_hit); пустой `street_q` → `[]` + `reason=empty_query`. `k` считает имена.
- `resolve_objects(name_ids, city_res, scope) -> list[ObjCand]` — раскрытие имён в объекты; при `resolved` — объекты этого города первыми, остальные с флагом `other_city`; при `none/unresolved` — все объекты в `scope`; для частых имён без города список обрезается до `scope`.
- `houses(street_id) -> list[Etalon]` — только для top-M (M ≤ 5) после ранжирования.
- `name_freq(name_id) -> float` — лог-частотность на словаре подключённой базы, нормированная.
Реализации: `BruteForce` (учебная: 631 имя, cdist, предсчитанные ключи), `NameVocab` (ГАР: инвертированный индекс по char-триграммам/фонетическим ключам словаря имён → top-200 → честный скор; шарды по регионам грузятся при старте, не лениво — П10). Бюджеты: BruteForce ≤ 1 мс, NameVocab ≤ 20 мс с городом / ≤ 50 мс без.

### 5.4 Ranker
Единица — объект (имя × город × тип). Фичи (таблица с типом, диапазоном, значением при отсутствии — в коде `features.py`): три сходства улицы [0,1]; `alias_hit` {0,1}; `type_match` {0,1,None→0.5}; `city_match` [0,1] (None → 0.5) и `city_status`; `house_found`, `house_in_list` {0,1}; `channel`; `name_freq`; `n_close` — число кандидатов в пределах δ от лидера (второй проход; p трактуется как вероятность при данном списке); interaction: `name_freq × city_match`, `name_freq × phonetic`, `channel × levenshtein`. Обучение: логрег (sklearn), на запрос — 1 позитив + все кандидаты выше отсечки как негативы; негативы вида 2 — все кандидаты как 0. Пост-калибровка (Platt/изотоническая) на val по стратам {channel} × {freq_class} × {city_status}. Fallback — ручные веса через сигмоиду с той же калибровкой (та же шкала). Переключение — конфиг `ranker: logreg|manual`. Выход — p «этот объект верный».

### 5.5 Decider
Вход: `RankedList[ObjCand + p]`, `CityResolution`, `ParseResult`, `asked_slot`, стоимости `{fa: N, ask: 1, confirm: c_conf, soft: c_soft}`. Пороги вычисляются: `answer`, если `(1 − p₁)·N < 1`, т. е. p₁ ≥ N/(N+1); аналогично для `answer_soft` и `confirm` с их стоимостями. Порядок правил (явный, П5):
1. `reject` — `has_address_cues = False` и `asked_slot = None`.
2. `ask_city` — лидер-имя частое (freq выше медианы) и `city_status ∈ {none, unresolved, ambiguous}` и объектов лидера в `scope` > 1 → `options` = ≤ 3 city_id по p; при > 3 — без options.
3. `ask_house` — лидер-объект уверен (p_obj ≥ порог confirm), но дом не найден / `ambiguous_number` / дом не в списке → `options` = ≤ 3 дома (учебная база); на ГАР при неполном списке — `answer_soft` с `house_unverified`.
4. `answer` / `answer_soft` / `confirm` — по ожидаемой цене; отрыв `p₁ − p₂` (p₂ := 0 при одном кандидате) входит в p через фичу `n_close`, отдельного δ нет.
5. `ask_street` — `city_status = resolved`, лидер ниже порога confirm, `has_address_cues = True`.
6. `reject` — остальное.
`slots_resolved` заполняется для `answer*`/`confirm`; `missing_slot` — только для `ask_*`. Пороги per-channel не нужны: канал внутри калибровки.

Проекция в формат ТЗ (полная): `answer`, `answer_soft`, `confirm` → эталоны лидера (≤ 3 по p; при `ask_house`-подобной неопределённости дома — дома одной улицы); `ask_city` → эталоны лидер-имени в городах из `options` по p; `ask_house` → ≤ 3 дома улицы-лидера; `ask_street` → `[]`; `reject` → `[]`. Пустой список в ТЗ = отказ.

### 5.6 Данные
- Учебные: `etalon.jsonl` (1000), `adresses_labeled.jsonl` (500: 400 voice / 100 webchat, 100 негативов, 37 пустых городов), `sample_input.jsonl` (50).
- ГАР: `gar_xml.zip` (53 ГБ) → выборочно `AS_ADDR_OBJ_*`, `AS_ADM_HIERARCHY_*`, типы, `AS_HOUSES_*` по регионам сети → `gar.sqlite` + словарь имён (нормализованных той же версией Normalizer).
- Синтетика: LLM-генерация ASR-вариантов по словарю имён (K7/K8), правила — fallback.

## 6. Метрики и приёмка

- Из ТЗ: top-1, top-3, reject_precision, reject_recall, p50/p95 мс. Отложенная выборка заказчика «того же формата» — допущение: тот же эталон; записать в readme.
- Свои: при заданном N — число ошибок `answer` на val (не доля: val ≈ 100 запросов, 0,97 неотличимо от 0,93); покрытие `answer`+`answer_soft`; график надёжности по стратам; распределение исходов; для `ask_house` — доля с верной улицей-лидером; для `ask_city` — доля с истинным городом в `options`.
- Замер времени: `match()` на прогретом индексе, монотонные часы, без загрузки эталона — словами ТЗ; железо и Python в readme.

| H11 | Подмена `BruteForce` → `NameVocab` на учебной базе не меняет top-1 более чем на 1 п.п. | run.py с обоими индексами | прогон |
| H12 | Диалоговая симуляция на labeled: после `ask_house` подаём истинный дом → `answer` в ≥ 95 %; после `ask_city` подаём истинный city_id → `answer`/`confirm` в ≥ 95 % | скрипт симуляции | прогон |
| H13 | Частые имена ASR искажает реже редких: доля ошибок улицы по квартилям `name_freq` монотонно убывает | подсчёт на labeled | прогон |

### Фаза C — эксперименты (по бюджету)

- C1. Сиамская char-модель на LLM-синтетике + HNSW по словарю имён — против трёх сигналов.
- C2. Ночной «майнер ошибок» (Р2.3): LLM по логам `reject`/`ask`/`confirm→нет` → кандидаты алиасов на ревью.
- C3. Асинхронное обогащение во время ответа человека (Р2.2) — при наличии GPU в проде.
- C4. TTS→ASR round-trip для проверки реалистичности синтетики.

## 9. Риски

| Риск | Эффект | Смягчение | Проверка смягчения |
|------|--------|-----------|--------------------|
| 500 строк мало для логрега | На отложенной выборке качество ниже | ≤ 15 фичей, L2, сравнение с ручными весами, синтетика | H3a: train/val ≤ 5 п.п. |
| Фонетический ключ сливает разные улицы | Ложные `answer` | Один из трёх сигналов; ранкер учит вес | H2 абляция в обе стороны |
| Дом с корпусами/литерами разобран неверно | Промах top-1 при верной улице | Тесты числительных; `ambiguous_number` → `ask_house`; top-3 из домов | A1 тесты, H12 |
| Отложенная выборка с другим распределением шума | Пороги сдвинуты | N выбирать с запасом (10, не 5); допущение в readme | — |
| Словарь имён ГАР больше 200 тыс. или cdist медленнее | H8 не сходится | Инвертированный индекс вместо cdist; Р1.2 радиус | H7, H8 |
| Разрешение города по 150 тыс. неточно | Объекты не того города первыми → `ask_city` чаще, не промах (Р1.1) | Город не фильтр; `other_city` в фичи | H8a |
| Типов улиц на ГАР много | Parser не режет строку | Типы из справочника через Index | B1 `DISTINCT type` |
| ПДн | Нельзя LLM API на запросе | Только офлайн-генерация по словарю имён (без ПДн), локальные модели | — |

## 10. Открытые вопросы

- Какую иерархию ГАР (административную или муниципальную) считать «городом» для слоя 2 — в ТЗ города административные; принять административную, зафиксировать.
- Нужны ли координаты в выходе для других пайплайнов (ГАР их не даёт; OSM — частично).
- Значение N (стоимость ложного `answer` в переспросах) — уточнить у заказчика; стартовое 10.
- Умеет ли бот заказчика хранить и возвращать канонические id слотов (иначе сужение — только фаззи).
