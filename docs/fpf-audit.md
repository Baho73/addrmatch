## 2. Дыры на границах блоков

**raw, slots → Normalizer**
- Пустая/None/огромная `raw` → «принимает `str`; пустая проходит как пустая; > 512 символов обрезается с флагом `truncated`».
- Слоты через Normalizer или нет → «слоты-тексты нормализуются той же функцией; слоты-id не трогаются».
- Канал не доходит до Normalizer, а правила разные → «Normalizer получает `channel`».
- Стоп-список мусора может съесть токен имени улицы → «Index при загрузке проверяет пересечение стоп-списка со словарём имён; владелец — Index».
- Неоднозначные числительные («сто, шестьдесят три») → «первое прочтение + флаг `ambiguous_number`; Decider трактует как основание для `ask_house`».
- Одна версия нормализации для эталона (офлайн) и запроса (онлайн) → «индекс хранит хэш версии Normalizer; несовпадение = ошибка».
- normalize(normalize(x)) == normalize(x) — заявить свойством с тестом.

**Normalizer → Parser**
- `street` обязателен, но при ответе на дозапрос его нет → «необязателен; полноту оценивает Decider».
- Флаг «похоже на адрес»: состав признаков и порог не заданы; ложные «не адрес» на позитивах не ограничены → «признак = тип ИЛИ дом ИЛИ токен из словаря имён (через `Index.has_name()`); ложный «не адрес» на 400 позитивах ≤ 1 %».
- Словарь типов улиц — чей (на ГАР типов на порядок больше: тер., СНТ, мкр., линия, км) → «типы приходят из справочника через Index».
- `city?` из строки без списка городов (N5) → «Parser города не извлекает; неопознанные токены до типа передаются как `city_hint`».
- Слот `street` дан И в raw есть улица → «слот побеждает».
- «16/2», «16-18», «д.16 кв.5» → перечислить формы и решение.
- Условие на выходе «дом найден» без целевого порога → задать (≥ 95 %).

**Parser → Index**
- `city_q = None` / `""` / «не разрешился» — три состояния → «None/"" → путь без города; неразрешённый (fuzzy < θ_city) → тот же путь + `city_status = unresolved`».
- Результат разрешения города не часть `Candidate`, а Decider на него опирается → «`CityResolution {status: resolved|ambiguous(list)|none, score}` отдельно».
- `street_type` не передаётся, хотя омографы разводятся типом → «передаётся как подсказка; в фичи, не в фильтр».
- `k` — имён или объектов → «имён; объекты раскрываются после блокинга».
- Пустой `street_q` → «[] и `reason = empty_query`, не исключение».
- Отзыв `NgramInverted` top-200 → гипотеза «recall@200 ≥ 0,98 на labeled с подменённым индексом».
- Список домов в Candidate на ГАР (десятки–сотни × 200 кандидатов) → «дома подтягиваются для top-M (M ≤ 5) после ранжирования, `Index.houses(street_id)`».
- Готовность индекса → `ready()`; вызов до готовности — ошибка.
- Бюджеты времени реализаций (BruteForce ≤ 1 мс, PerCity ≤ 5 мс, Ngram ≤ 50 мс) — в контракт реализации.

**Index → Ranker**
- Типы/диапазоны фичей, значения при пропуске (город None → fuzzy = ?) → таблица фичей.
- «Частотность имени» — на каком словаре → «на словаре подключённой базы; лог, нормированный на размер словаря; хранится в индексе».
- «Число близких кандидатов» — фича множества, два прохода; p зависит от соседей → зафиксировать: «p — вероятность при данном списке».
- Обучающая выборка: негативные кандидаты на запрос, негативы вида 2 → «1 позитив + все кандидаты выше отсечки; вид 2 — все как 0».
- Логрег при дисбалансе не откалиброван → «Platt/изотоническая на val; график надёжности в readme».
- Ручные веса как fallback — не вероятность → «сигмоида + калибровка на val, та же шкала [0,1]».
- Кто переключает логрег/ручные → задать.

**Ranker → Decider**
- Вход Decider — не только p_top1/p_top2 → «`RankedList` (name_id, city_id, type, p, houses) + `CityResolution` + `ParseResult`».
- Порядок правил (П5) → «reject-по-признакам → ask_city → ask_house → answer → confirm → ask_street → reject».
- Один кандидат → «p_top2 := 0».
- `options`: максимум/порядок/при > 3 → «≤ 3 по p; при > 3 — `ask_city` без options».
- «Дом не в списке» на ГАР (список неполный) → выбрать: `answer` с `house_unverified` или `ask_house`.
- Пороги τ_a, τ_c, δ: где живут, per-channel? → задать сейчас («конфиг ранкера, per-channel»).
- `confirm` обязан вернуть канонические слоты (city_id, street_id, house), чтобы бот вернул их слотами (П6).
- `missing_slot` для `confirm`/`answer`/`reject` → None.

**Decider → бот / run.py**
- `candidates` при `answer` → «всегда ≤ 3 эталона по p; `decision` отдельно».
- `ask_city` с лидером в 3 городах → порядок эталонов в проекции.
- Исключения → «`match()` никогда не бросает; `reject` + `error`; ошибки загрузки — на `ready()`».
- Точка замера → «внутри match(), монотонные часы»; ТЗ разрешает исключить загрузку и прогрев — записать в readme этими словами.
- `scores` — калиброванные p или сырые; кто владеет порогами → решить до A6.
- Разложение по сигналам (N6) → поле `explain` или снять N6.
- `ask_street` без лидера → пустой список = «отказ» по ТЗ, при наличии истины бьёт reject_precision. Таблицу проекции записать полностью (в concept усечена).

## 3. Обязательства без доказательства

**Требования без гипотезы/теста**
- N2 — нет теста «чистая машина». Дёшево: свежий venv на другой машине/CI.
- N3 — проверяется только H7, H8, B2. Нет проверки переноса калибровки (П4), нет размеченных данных ГАР — на чём мерить?
- N4 — нет отношения стоимостей; 0,97 и 0,8 — с потолка. Направление подтверждено ТЗ — записать цитату.
- N5 — нет теста; дёшево: граф импортов (`numerals`, `normalizer`, фаззи-движок не импортируют `index`/данные).
- N6 — нет носителя и метрики (П11).
- K1 — H1 проверяет комбинацию, а не K1 против альтернативы (матч целой строкой). Абляции нет.
- K5 — нет прямой проверки точности фаззи-разрешения города. Критический разрез П2. «10 % кривых городов» = 7,4 % пустых + неизмеренное.
- K6 — тесты A6 проверяют, что ветка исполняется, а не что дозапрос уместен (доля `ask_house` с верной улицей-лидером; доля `ask_city` с истинным городом в options). Нет диалогового теста: после `ask_house` подаём истинный дом → `answer`?
- K7 — нет теста до фазы C; «10–20 %» не измерено (измеримо после A5 как доля confirm+ask).
- F.1 «частые имена ASR не искажает» — без данных; на нём стоит H10.

**Гипотезы, где тест измеряет не то**
- H9: «доля labeled, которые генератор умеет породить» — достижимость, не похожесть. Проверяет только «обучено на синтетике → качество на labeled» против «обучено на labeled».
- H4: одна сторона (ловля негативов); ложные «не адрес» на позитивах не ограничены.
- H3: нет статистической мощности. При сплите 75/25 val ≈ 100–125, `answer` ≈ 80–100; 0,97 = ≤ 3 ошибки; ДИ при 2/90 ≈ 0,5–8 %. 0,97 от 0,93 не отличить. Записать «ошибок ≤ 3 на val», признать ограничение.
- H10: 37 строк, одна = 2,7 п.п. — шум.
- H1: «на 400 позитивах, val-сплит» — противоречие в ячейке. A3 (ручные веса) — на 400; A5 — только val.
- H8: меряет перебор внутри города, но не разрешение города по 150 тыс. населённых пунктов; по цифрам авторов cdist по 150 тыс. — десятки мс, тот же порядок, что NgramInverted. Латентность пути «с городом» на ГАР не проверена.
- H5 и H3 крутят один порог по разным критериям — приоритет не задан.
- H7: `COUNT(DISTINCT name)` сырого или нормализованного? Размер словаря зависит от Normalizer.

**Дизайн против прогона (смешано)**
- §4 «Почему» — дизайн-рассуждения как факты («дом решает top-1», «словарь почти закрыт», «фонетика для voice») без измерений.
- «Город кривой/пустой в 10 %» — 7,4 % измерено, остальное предположено.
- K4 + H7 оформлены правильно (оценка + прогон); так же оформить остальные утверждения §4.
- §9 «Смягчение» — ни одно не имеет проверки (например «≤ 12 фичей, регуляризация» → тест: train vs val расходятся ≤ N п.п.).

## 5. Итог для ТРИЗ

**Т1. Город: фильтр и не фильтр (П2).** Улучшаем латентность на ГАР (перебор 1–4 тыс. вместо 1,3 млн) и разводку одноимённых улиц → город должен жёстко отсекать шард. Ухудшается устойчивость к кривому/пустому городу (≥ 7,4 %) → город не должен отсекать. Элемент: `city_q` на входе Index. Параметры: время поиска (мс) ↔ отзыв правильной улицы при ошибочном городе (%).

**Т2. Каскад: точность и латентность/CPU (П3).** Улучшаем точность `answer` и покрытие на неуверенных 10–20 % (тяжёлая модель). Ухудшаются p95 (200 → 300–1000 мс) и «CPU, без GPU» (N2). Элемент: один синхронный `match()`. Параметры: доля верных среди `answer` ↔ p95 (мс), наличие GPU в резервном пути.

**Т3. Один порог на две популяции (П7 + F.1).** Улучшаем точность `answer` (τ_a вверх) — падает покрытие (H3 ≥ 0,8); H5 и «запас в сторону confirm» давят тот же порог. Обострение: частые имена решает город (фонетика бесполезна), редкие — фонетика (город почти не нужен), а веса и порог одни. Условный — после калибровочной кривой A5.

**Т4 (пограничный).** Флаг «похоже на адрес»: строгий для ловли «не про адрес» (H4) ↔ мягкий для односложных ответов на дозапрос. Снимается контекстом («какой слот спрашивали»); ТРИЗ только если бот не передаёт контекст.

**Не в ТРИЗ, закрыть текстом до A3:** П1, П4, П5, П8, П9.
