# ТРИЗ-разрешение противоречий концепции addrmatch

Дата: 2026-09-12. Вход: три противоречия из внутреннего аудита спецификации (Т1–Т3). Матрица: `user2001_business` (28 параметров). Приёмы — из ячеек матрицы через MCP `triz`, номера по Альтшулеру.

---

## Т1. Город: фильтр и не фильтр

**Техническое противоречие.** Улучшаем скорость поиска на ГАР и разводку одноимённых улиц (жёсткий срез по городу: 1–4 тыс. имён вместо 1,3 млн) — ухудшается надёжность: при кривом/пустом городе (≥ 7,4 %) правильная улица не попадает в кандидаты, ранкер бессилен.

**Физическое противоречие.** `city_q` на входе Index должен отсекать кандидатов (скорость, разводка) и не должен отсекать (устойчивость к ошибке города).

**Ячейки матрицы.** Скорость (3) × Надёжность (22): **35** изменение параметров, 21 проскок, **11** подушка, **28** замена схемы. Точность (13) × Надёжность (22): 32 метки, **3** местное качество, 11, **23** обратная связь. Скорость (3) × Устойчивость (5): **15** динамичность, 18, 33, 28.

**ИКР.** Город сужает поиск ровно настолько, насколько ему можно верить; когда верить нельзя — его как бы нет, а скорость от этого не страдает.

### Решения

**Р1.1 (рекомендуемое). Блокинг не по городу, а по словарю имён — прим. 28 + 35.**
Заменить объект фильтрации: скорость на ГАР нужна была против 1,3 млн *объектов*; но поиск идёт по 100–200 тыс. *имён* (F.1), и это уже влезает без города: инвертированный индекс по char-триграммам/фонетическим ключам → top-200 имён за единицы мс, `cdist` по 150 тыс. коротких строк — десятки мс. Город переезжает из Index-фильтра в слой 2 (имя → объекты) и в фичу ранкера. Противоречие исчезает: скорость даёт словарь имён, разводку одноимённых — город на слое объектов, а при кривом городе имя всё равно найдено → `ask_city` вместо промаха.
Архитектура: `Index.candidates(street_q, k)` без `city_q`; `Index.resolve_objects(name_id, city_resolution)` — второй вызов; `CityResolution` — вход ранкера и Decider, не Index.

**Р1.2. Раскрывающийся радиус по обратной связи — прим. 23 + 15 + 11.**
Если словарь имён на конкретной базе всё же велик (или нужны ещё меньшие мс): сначала шард города; если лучший скор улицы < θ_widen или город не разрешён — расширить: регион → национальный индекс имён. Фильтр динамический: жёсткий, пока даёт уверенный результат, исчезает, когда не даёт. 90 % запросов остаются в мс, ~10 % платят 20–50 мс — что и есть N1 «без города ≤ 50 мс».
Архитектура: `Index.candidates(street_q, scope=[city_id] | region | None)`, Decider/оркестратор вызывает повторно с расширенным scope; `reason=widened` в фичи ранкера.

**Р1.3. Местное качество по частотности имени — прим. 3.**
Частые имена («Ленина», «Мира») обязаны иметь разрешённый город (иначе `ask_city`), редкие («Хользунова») принимаются по фонетике без города. Частотность имени известна из словаря → правило ветвления в Decider и взаимодействие фич в ранкере (`freq × city_match`, `freq × phonetic`). Снимает не сам конфликт скорости, а его следствие — ложные `answer` при пустом городе.

**Вердикт.** Р1.1 как база (контракт Index меняется сейчас, до A3 — пока дёшево), Р1.3 в ранкер/Decider, Р1.2 в запас на случай, если Р1.1 не уложится в бюджет на реальном словаре ГАР (H7 покажет).

## Т2. Каскад: точность и латентность/CPU

**Техническое противоречие.** Улучшаем точность и покрытие на неуверенных 10–20 % (тяжёлая модель: LLM-нормализатор/реранкер) — ухудшается p95 (200 → 300–1000 мс) и нарушается «CPU, без GPU в резервном пути» (N2).

**Физическое противоречие.** `match()` должен быть быстрым и лёгким (CPU, мс) и должен быть тяжёлым и умным (GPU, сотни мс).

**Ячейки матрицы.** Качество (25) × Скорость (3): **14в** замкнуть выход на вход, **15**, **8** антисвойство, **26** копирование, **3**, **10** предварительное исполнение. Точность (13) × Время (4): 3, **10**, 16, **24** посредник. Качество (25) × Сложность (19): **2** вынесение, **13** наоборот, 28, 16, 37.

**ИКР.** Тяжёлая модель улучшает ответы, не присутствуя в момент ответа.

### Решения

**Р2.1 (рекомендуемое). Тяжёлое — на этапе сборки, лёгкое — на запросе — прим. 10 + 26.**
LLM работает офлайн: по словарю имён генерирует ASR-варианты («киравсгой», «дзержинскага», склейки), из них дистиллируются дешёвые артефакты — расширенный словарь вариантов, матрица замен для взвешенного Левенштейна (A4), обучающая выборка для сиамской char-модели (B3) и ранкера. На запросе — только CPU-мс. Противоречие исчезает разделением во времени: GPU нужен один раз при сборке индекса, в резервном пути его нет. Заодно закрывает K8/E1 (синтетика) и H9 — синтетика из LLM реалистичнее правил.
Архитектура: `tools/build_variants.py` (офлайн, LLM) → `variants.jsonl` → Index грузит как алиасы имён; ранкер получает фичу `alias_hit`.

**Р2.2. Диалог как буфер латентности — прим. 14в + 24 + 15.**
На неуверенном запросе матчер мгновенно отдаёт `confirm`/`ask_*` (мс), а тяжёлая модель запускается асинхронно и работает пока человек отвечает (2–5 с речи). К следующему ходу её результат уже есть и уточняет кандидатов или снимает вопрос («да, Кировская 16 — записываю»). Тяжёлый путь никогда не в синхронных 200 мс; латентность спрятана в естественную паузу надсистемы — диалога. Требует GPU в проде, но не в резервном пути `match()`; для ТЗ — описать как «что дальше».
Архитектура: `match()` синхронный; `enrich_async(query_id)` — отдельный сервис, результат в слот `hint` следующего вызова.

**Р2.3. Тяжёлое как ночной «майнер ошибок» — прим. 2 + 13 + 23.**
Вынести LLM из запроса вообще: она разбирает логи `reject`/`ask_*`/`confirm→нет` за сутки, предлагает новые алиасы имён и правила Normalizer, человек/тест их подтверждает, индекс пересобирается. Система учится на своих промахах, качество растёт от недели к неделе без GPU в проде. Не помогает конкретному звонку сейчас — помогает следующим.

**Вердикт.** Р2.1 — в план сразу (фаза B4/B5, заменяет генератор синтетики правилами); Р2.3 — как петля эксплуатации; Р2.2 — для продукта при наличии GPU, в readme как направление. K7 «каскад в запросе» из ключевых решений убрать.

## Т3. Один порог на две популяции

**Техническое противоречие.** Улучшаем точность `answer` (τ_a вверх) — падает покрытие `answer` (H3 ≥ 0,8; H5 и «запас в сторону confirm» давят тот же порог). Обострение: частые имена решает город, редкие — фонетика, а веса и порог общие.

**Физическое противоречие.** Порог τ_a должен быть высоким (точность) и низким (покрытие); ранкер должен доверять городу (частые имена) и не доверять городу (редкие имена).

**Ячейки матрицы.** Точность (13) × Производительность (21): **1** дробление, **10**, 34, **28**. Надёжность (22) × Производительность (21): **35**, 1, 10, 38. Качество (25) × Производительность (21): 35, 1, 18, 38, **37** интенсивность.

**ИКР.** Порог сам знает, в какой ситуации он находится; одна цифра, верная в каждой страте.

### Решения

**Р3.1 (рекомендуемое). Дробление калибровки, не порога — прим. 1 + 3.**
Конфликт возникает потому, что один скор означает разную вероятность ошибки в разных стратах (voice/webchat × частое/редкое имя × город разрешён/нет). Лечится не разными τ, а калибровкой *внутри страт* (изотоническая/Platt по группам) и фичами-взаимодействиями в ранкере (`freq × city_match`, `freq × phonetic`, `channel × levenshtein`). После этого p = вероятность в каждой страте, и единый τ_a даёт заявленную точность по определению. Противоречие исчезает: один порог, но на честной вероятности.
Архитектура: `Ranker.fit()` — логрег с interaction-фичами + пост-калибровка по стратам; `Ranker.reliability_report()` в readme (график надёжности по стратам).

**Р3.2. Порог выводится из стоимостей, а не подбирается — прим. 28.**
Заменить объект «порог» функцией «ожидаемая цена решения». Задать C_fa (ложный `answer`: человек уехал не туда) и C_ask (переспрос: ~10 с диалога). Decider выбирает исход с минимальной ожидаемой ценой: `answer`, если `(1 − p) · C_fa < C_ask`, т. е. τ_a = C_ask / (C_ask + C_fa). Единственная ручка — отношение стоимостей из бизнеса (закрывает П1/N4: «1 ложный answer = N переспросов»). Точность и покрытие становятся следствием, а не двумя требованиями на одну ручку; спор «0,97 vs 0,8» переезжает к заказчику как одно число N.
Архитектура: `Decider(costs={fa: N, ask: 1, confirm: 0.5})`; τ вычисляются, в конфиге хранится N, не τ.

**Р3.3. Снизить цену ошибки, а не поднимать порог — прим. 37 + 8.**
Градация интенсивности `answer`: вместо бинарного «записал / переспросил» — «записываю Кировская 16, если ошибся — поправьте» (произнесённый адрес = неявное подтверждение, человек поправит). C_fa падает в разы → по Р3.2 τ_a опускается → покрытие растёт без потери безопасности. Противоречие снимается в надсистеме (диалог), а не в матчере.
Архитектура: исход `answer_soft` между `answer` и `confirm`; для проекции в формат ТЗ = `answer`.

**Вердикт.** Р3.1 + Р3.2 вместе в A5 (калибровка по стратам, τ из N); Р3.3 — в дизайн диалога бота, в readme как рекомендация.
